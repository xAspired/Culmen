# Code of conduct

## The short version

Be decent. Assume good faith. Argue about the work, not the person.

## What is expected

This is a technical project about getting numbers right. The behaviour that
makes that possible:

- **Disagree with the work, specifically.** "This is wrong because the
  reference plane for G/T does not match the losses" is what we want. "This is
  wrong" is not, and neither is anything about the person who wrote it.
- **Say what you do not know.** "I could not verify this" is one of the most
  useful sentences in this repository and appears throughout it. Nobody is
  penalised for it; several defects here were found because somebody admitted
  an unknown instead of covering it.
- **Take correction without drama, and give it without any.** Everyone here
  has shipped a bug. This project's own history includes a scheduler that
  double-counted data and an optimiser that gave up after one iteration and
  reported success.
- **Respect the maintainer's time and the contributor's.** Read the existing
  ADRs before reopening a settled decision; explain a rejection rather than
  closing in silence.

## What is not acceptable

Harassment, insults, or personal attacks. Discrimination or demeaning comments
on any basis. Unwelcome sexual attention. Publishing someone's private
information. Sustained disruption of discussion. Encouraging any of the above.

This applies in issues, pull requests, commit messages, code comments and
anywhere else the project is conducted.

## Enforcement

Report a problem to the maintainer privately, through the contact address in
the repository's GitHub profile. Reports are handled discreetly.

The maintainer may edit or remove contributions, and may block accounts, when
this document is not followed. For anything beyond an isolated lapse, an
explanation of the decision will be given to the person concerned.

## Scope

This applies in project spaces, and in public spaces when someone is
representing the project.

---

This is a deliberately short, project-specific document rather than an adopted
standard text. If the project grows enough to need the process machinery of
the [Contributor Covenant](https://www.contributor-covenant.org/), adopting it
verbatim is the right move at that point — and it supersedes this file rather
than being blended into it.
